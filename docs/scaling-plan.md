# Workerスケール設計 — 50店舗 / 月12万円ポッド構想の検証

作成: 2026-08-08(同日修正: 12万円=50店舗単位) / ステータス: ドラフト(EC2実測の追記待ち)

## 1. ターゲット(提案スケッチの言語化)

- 単位経済: **50店舗ポッドあたり EC2費 月12万円**(≈2,400円/店舗)
- ポッド構成: ジャンル(ヘア/キレイ)× 種別(予約/取込/投稿)= **6レーン**、各レーンに本体+FBの2台 = **12台×約1万円**
- スケール方式: 51店舗目からは同型ポッドを追加(+12万円/50店舗)

**実測からの結論:**

1. **常時系c6i.2xlargeは大幅な過剰**。瞬間ピークでも8vCPU中約2.7vCPU相当・メモリは1割未満。CPUバウンドでもRAMバウンドでもなく、**制約は完全に外部(SBアカウント直列・IP・ペーシング)**と確定
2. ⚠️ **ルートディスクが91%(18G/20G)で逼迫** — デバッグcapture/ログ/userDataDirの蓄積。即対応が必要(掃除cron+gp3 50GBへ拡張で+約300円/月)
3. FBはほぼアイドル(設計どおり)。m6i.large は FB 用途には過剰

### 即時の最適化(50店舗を待たず実施可能)

| アクション | 効果 |
|---|---|
| 常時系を c6i.2xlarge → **c7g.xlarge(4vCPU/8GB ARM・約1.6万円)** または c6i.xlarge(約2.3万円) | 月**2.4〜3.1万円削減**。ピーク33.7%×2=67%相当で安全圏 |
| FB/bulk を m6i.large → **t4g.medium(約4,900円)** ×2 | 月約1.8万円削減(FBは失敗時のみ稼働・bulkは深夜集中) |
| ディスク掃除cron(salonboard-debug 30日ローテ)+gp3拡張 | 障害予防 |

→ 即時最適化後: **約3.0〜3.5万円/月(15店舗)≈ 2,000〜2,300円/店舗**。50店舗ポッドの単位経済(2,400円/店舗)と整合。

## 3. 容量モデル(50店舗ポッド)

スケール係数: 50店舗 ÷ 15店舗 ≈ **3.3×**

| 項目 | 50店舗時の推定 | 根拠 |
|---|---|---|
| ジョブ量 | 約3,500〜5,000 job/日 | 線形外挿 |
| ピーク | 約330 job/時 ≈ 6 job/分 | 線形外挿 |
| 必要同時Chrome | **ピーク6〜10並行**(平均60〜90秒/job) | 待ち行列余裕込み |
| RAM要件 | 1Chromeコンテキスト ≈ 0.4〜0.7GB + userDataDir | 実測要追記 |

**→ 計算資源としては t4g.large(2vCPU/8GB)×2〜3台で捌ける規模。12台ポッドは容量2〜4倍の余裕を持つ構成**であり、その意味は「分離」(レーン独立・デプロイ影響範囲・セッション分散・CAPTCHA時の巻き添え防止)にある。余裕がある分、**1レーンあたりの負荷が軽くログイン密度も下がるため、CAPTCHA/throttle耐性の観点では合理的**。

### 本当のスケール制約(EC2以外)

| 制約 | 内容 | 50店舗時の対応 |
|---|---|---|
| SBアカウント直列 | 同一アカウント同時1セッション | 店舗(アカウント)を**レーン内でシャード**すれば横に伸びる |
| static ISP IP | 現行10本・店舗→IP sticky | **店舗数比例で増設必須**(50店舗で30〜50本規模。Decodo追加費用: 要見積・EC2予算外) |
| ログインペーシング/CAPTCHA | endpoint/アカウント単位 | 12台分割でログイン密度が下がり改善方向 |
| CAPTCHA避難レーン | PC affinity必須 | PC 2台へ増設(50店舗を分担カバー) |
| Supabase/Admin | ジョブ基盤・API | 50店舗では余裕(ボトルネックにならない) |

## 4. 提案スケッチの検証と修正提案

### 成立性: **予算内で成立する**

t4g.large(ARM, 2vCPU/8GB)= 東京 約**9,800円/月**(オンデマンド概算・EBS gp3 30GB 別途約400円)→「1台1万円」の想定どおり。**12台で約11.8万円 ≒ 12万円** ✓

### 修正提案(ポッド内の割り方だけ変える)

1. **ジャンル分割(ヘア/キレイ)をやめ、店舗シャード分割に** — hair/estheticはコード内のURL/DTO差分でありリソースと無関係。同じ6レーンでも「予約シャードA(店舗1-25)/予約シャードB(店舗26-50)」のほうが、アカウント直列のボトルネックが実際に半分になる
2. **FB 6台は縮約可能** — FB稼働は全処理の1%未満。**FB共有2台**にすれば4台(約4万円)浮き、**static ISP増設(+20〜30本)とPC 2台目**という"真の制約"側に予算を回せる
3. ただし**スケッチ忠実(A案)でも予算内で成立**するため、シンプルさ優先ならAで開始→運用データでB化も可

### 構成案比較(50店舗ポッド・月額概算)

| 案 | 構成 | EC2月額 | 特徴 |
|---|---|---|---|
| A: スケッチ忠実 | 本体6台+FB6台(全てt4g.large) | **約11.8万** | 予算どおり。レーン対称でわかりやすい |
| B: シャード最適化(推奨) | 予約A/B・取込A/B・投稿・bulk=本体6台+**FB共有2台** | **約7.9万** | 残り約4万をISP増設+PC2台目へ(制約解消に直結) |
| C: 現行踏襲 | c6i.2xlarge×2+FB×1 | 約12.5万 | 変更最小・分離なし・ARM検証不要 |

案Bのポッド内レーン割り:

```
[予約シャードA] 店舗1-25の予約系      [予約シャードB] 店舗26-50の予約系
[取込シャードA] 店舗1-25のfetch系     [取込シャードB] 店舗26-50のfetch系
[投稿+設定反映] ポッド内全店舗(量少)  [bulk/一括取込] 連携開始時のみ負荷
[FB共有×2]     レーン横断・失敗時のみ
```

- 進行中の**lane split(claim p_lane)をシャード条件に拡張**するだけで実装可能。ワーカーコード変更は最小
- ARM(t4g)前提のため**arm64ビルド検証が必要**(Playwright/Chromiumはarm64対応済み。x86なら t3.large≈1.23万/台で約+2.8万)

## 4.5 自動スケール設計 — 「店舗が増えても手作業ゼロ」の実現

50→100店舗以降、**店舗追加のたびに人がインフラを触る運用を廃止する**ための設計。

### 原則

1. **店舗のオンボードはデータ操作だけで完結する**(インフラ作業ゼロ)
2. インフラの増減は「宣言(Terraform)+自動判断(メトリクス)」で行い、人は承認だけ
3. セッション(Chromeプロファイル)は消えても自動再シードできる前提を維持する(実証済み)

### 仕組み(3層)

```
[Layer 1] shop→shard自動割当(DB)
  salonboard_worker_shards: shard_id / capacity / current_load
  ・新店舗の連携開始トリガ → 最少負荷shardへ自動割当(1行INSERT)
  ・claim RPCは「自shardの店舗のみ」を返す(lane×shard条件)
  ・shard間の店舗移動もUPDATE1行(次のclaimから反映・無停止)

[Layer 2] ワーカーのセルフサービス化
  ・インスタンスはEC2タグ(Shard/Lane)を起動時に読み自己構成
  ・同一AMI/起動テンプレートで全レーン共通(役割はタグだけで決まる)
  ・増設 = Terraformのcount+1(または ASG desired+1)のみ。コード変更なし

[Layer 3] 容量ウォッチャー(段階導入)
  Phase A(手動承認型): 毎分cronがshard別のqueue深さ/予約p95を監視
    → 閾値超過でSlack警報「shard#2が飽和。増設コマンド: terraform apply -var=...」
  Phase B(自動型): CloudWatchカスタムメトリクス(shard queue depth)
    → ASGスケールアウト → 新インスタンスがタグで自動参加
```

### スケールに連動する非EC2リソースの扱い

| リソース | 自動化方針 |
|---|---|
| static ISP(Decodo) | 完全自動購入は不可 → **在庫閾値アラート**(空きIP<5本でSlack警報・リードタイム込みで前倒し発注)。店舗→IP割当自体は既存pickProxyで自動 |
| PC(CAPTCHA避難レーン) | 台数はアラート運用(担当店舗数>25/台で警報)。**アカウント追加ログインの手順書化+将来はSB認証情報からの半自動セットアップ** |
| Supabase | 50-100店舗はプラン内。接続数のみ監視項目に追加 |

### なぜECS/Fargateにしないか(検討済みの結論)

Chromeの**永続プロファイル(セッション)+ステルス指紋の安定性**がEC2+EBSに強く依存するため。
Fargateはタスク再配置でプロファイルが消え、全店再ログイン→CAPTCHA/throttleの波を誘発する(6/27・8/7の実障害と同型)。EFSはChromeプロファイルのlock/レイテンシと相性が悪い。**「EC2+EBS+タグ自己構成+ASG」が現実解**。

### 実装ステップ(タスク化)

1. shard割当テーブル+claim拡張(進行中のlane split p_laneに相乗り)— DB/worker 2日
2. EC2タグ自己構成+Terraformモジュール化(起動テンプレート共通化)— 2日
3. 容量ウォッチャーPhase A(cron+Slack警報)— 1日
4. ISP在庫アラート — 0.5日
5. (50店舗到達後)Phase B自動増設

## 5. 段階移行プラン(15→50店舗)

| フェーズ | 店舗数 | アクション | トリガー |
|---|---|---|---|
| 現状 | 15 | 現構成維持+EC2実測の取得+arm64検証 | - |
| Step1 | 〜25 | 予約レーンを専用台へ分離(ポッドの最初の1台) | 予約p95が3分に接近 |
| Step2 | 〜35 | 取込レーン分離+FB共有化+ISP増設(+10本) | 取込がpeak帯で予約と競合 |
| Step3 | 〜50 | シャードA/B分割完成(ポッド完成形)+PC2台目 | 36店舗目以降のオンボード |
| Step4 | 51〜 | **ポッド#2を新設**(+12万円/50店舗) | 51店舗目 |

各Stepは**claim条件(lane+shard)の変更のみ**で店舗を無停止で移せる設計とする。
