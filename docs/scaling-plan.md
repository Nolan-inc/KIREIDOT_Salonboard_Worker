## 1. ターゲット(提案スケッチの言語化)

- 予算: **EC2費 月12万円**
- 規模: **100店舗**(50店舗ブロック×2)
- 分割案: ジャンル(ヘア/キレイ)× 種別(予約/取込/投稿)= 6レーン/ブロック、各レーンに本体インスタンス(約1万円/台)+FBインスタンス
- → 本体12台×約1万円 = 12万円

## 3. 容量モデル

スケール係数: 100店舗 ÷ 15店舗 ≈ **6.7×**

| 項目 | 100店舗時の推定 | 根拠 |
|---|---|---|
| ジョブ量 | 7,000〜10,000 job/日 | 線形外挿 |
| ピーク | 約700 job/時 ≈ 12 job/分 | 線形外挿 |
| 必要同時Chrome | **ピーク12〜20並行**(平均60〜90秒/job) | 待ち行列余裕込み |
| RAM要件 | 1Chromeコンテキスト ≈ 0.4〜0.7GB + userDataDir | 実測要追記 |

**→ 純粋な計算資源としては t4g.large(2vCPU/8GB)クラス×3〜4台でピークを捌ける規模。**
**12台構成は容量的には過剰であり、意味は「分離」(デプロイ影響範囲・レーン独立・セッション分散)にある。**

### 本当のスケール制約(EC2以外)

| 制約 | 内容 | 100店舗時の対応 |
|---|---|---|
| SBアカウント直列 | 同一アカウント同時1セッション | 店舗(アカウント)を**インスタンスにシャード**すれば横に伸びる |
| static ISP IP | 現行10本・店舗→IP sticky | **店舗数に比例して増設必須**(Decodo追加費用: 要見積・EC2予算外) |
| ログインペーシング/CAPTCHA | endpoint/アカウント単位 | シャード分割でむしろ改善(1箱あたりのログイン密度低下) |
| CAPTCHA避難レーン | PC affinity必須 | PC 2〜3台へ増設(全アカウントを分担カバー) |
| Supabase/Admin | ジョブ基盤・API | 現行構成で10×余裕(ボトルネックにならない見込み) |

## 4. 提案スケッチの検証と修正提案

### 成立性: **予算は成立する**

t4g.large(ARM, 2vCPU/8GB)= 東京 約**9,800円/月**(オンデマンド概算・EBS別途400円程度)→「1台1万円」の想定と一致。12台で約11.8万円。

### 修正提案(同予算でより効く割り方)

1. **ジャンル分割(ヘア/キレイ)は不要** — hair/estheticはコード内のURL/DTO差分であり、リソース・アカウント構造とは無関係。分割軸は**店舗シャード**(=SBアカウントの集合)にすべき
2. **FBを12台にしない** — FB稼働は失敗時のみ(直近7日で処理の1%未満)。**共有FB 2台**(各50店舗ブロックに1台)で十分
3. 浮いた予算の使途: **static ISP増設**(スケールの真の制約)+**PC 2台目**(CAPTCHA避難レーンの冗長化)

### 構成案比較(月額概算・東京リージョン)

| 案 | 構成 | EC2月額 | 特徴 |
|---|---|---|---|
| A: スケッチ忠実 | 本体12台(t4g.large)+FB12台(t4g.medium×12≈5.9万) | **約17.7万** | FB分で予算超過。分離は最大 |
| B: レーン×シャード(推奨) | 予約2+取込2+投稿1+bulk1=**本体6台(t4g.large)**+**FB共有2台**+予備1台 | **約8.8万** | 予算内。残り3万を ISP増設/PC2台目/監視 に回せる |
| C: 現行踏襲スケールアップ | c6i.2xlarge×2+FB×1 | 約12万 | 変更最小だが分離なし・デプロイ影響大 |

案Bのレーン割り(1ブロック=50店舗):

```
[予約シャード1] 店舗1-50の予約系   [予約シャード2] 店舗51-100の予約系
[取込シャード1] 店舗1-50のfetch系  [取込シャード2] 店舗51-100のfetch系
[投稿+設定反映] 全店舗(量が少ないため共有1台)
[bulk/一括取込] 全店舗(連携開始時のみ負荷)
[FB共有×2]     シャード横断で失敗時のみ稼働
```

- 既に進行中の**lane split(realtime/bulk)のclaim p_lane機構をそのまま拡張**(p_lane + shop shard条件)で実装可能。ワーカーコード変更は最小
- ARM(t4g)前提のため**arm64ビルドの検証が必要**(Playwright/Chromiumはarm64対応済み。未検証ならx86のt3.large≈1.23万/台で+2〜3万)
